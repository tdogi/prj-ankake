# Project Ankake オンライン対戦バックエンド仕様書

## 1. 概要

Project Ankakeにオンライン対戦機能を追加する。

バックエンドにはSupabaseを使用し、オンライン対戦に必要な機能のみを担当させる。

カード、デッキ、カード効果、ゲームルールなどは既存のフロントエンド実装を継続して使用する。

また、開発時には本番環境へ接続せずにオンライン対戦機能を検証できるローカルサーバを用意する。

---

## 2. 基本方針

バックエンドでは主に以下を管理する。

* マッチング
* 対戦中の一時的なプレイヤー情報
* 対戦状態
* プレイヤー間のリアルタイム同期
* 不要になった一時データの削除

以下はバックエンドでは管理しない。

* カード情報
* デッキ情報
* 永続ユーザー情報
* 戦績
* ランキング

---

## 3. ユーザー

アカウント登録機能は実装しない。

対戦開始時にユーザー名のみ入力する。

ユーザー名は以下の期間のみ保持する。

* マッチング待機中
* 対戦中

対戦終了後は削除する。

ユーザー名は重複を許可する。

システム内部でプレイヤーを識別するため、一時的なIDを使用する。

永続的なユーザー識別は行わない。

---

## 4. マッチング

マッチング開始時に以下を入力する。

* ユーザー名：必須
* 合言葉：任意
* 使用デッキ：必須

### ランダムマッチ

合言葉が未入力の場合、同じく合言葉を設定していない待機中ユーザーとランダムマッチする。

複数の待機ユーザーがいる場合は、原則として待機時間の長いユーザーを優先する。

### 合言葉マッチ

合言葉が入力されている場合、同じ合言葉を入力したユーザー同士のみをマッチングする。

合言葉そのものはDBに平文保存しない。

---

## 5. 対戦

マッチング成立後、対戦ごとに一意な対戦IDを発行する。

対戦中は少なくとも以下を管理する。

* 対戦ID
* Player 1の一時ID
* Player 1のユーザー名
* Player 2の一時ID
* Player 2のユーザー名
* 対戦状態
* ゲーム状態
* 最終更新日時

対戦中の正式なゲーム状態はSupabase側に保持し、両プレイヤー間で同期する。

ゲーム状態の詳細構造は既存のフロントエンド実装に合わせて決定する。

---

## 6. リアルタイム通信

Supabase Realtimeを使用して対戦状態を同期する。

主に以下を同期対象とする。

* 対戦開始
* プレイヤー操作
* ターン進行
* ゲーム状態更新
* 対戦終了
* 切断・再接続

具体的な通信方式やイベント設計は、既存実装を確認した上でCodexが適切な方式を選択する。

---

## 7. データ保持

バックエンドに保存するデータは原則として一時データとする。

### マッチング待機中

待機ユーザー情報を保持する。

マッチング成立または待機キャンセル後に削除する。

### 対戦中

対戦に必要なユーザー情報およびゲーム状態を保持する。

### 対戦終了後

対戦データを削除する。

以下は永続保存しない。

* ユーザー名
* 一時プレイヤーID
* ゲーム状態
* 対戦結果
* 対戦履歴

ブラウザ終了や通信切断によってデータが残る場合を考慮し、一定時間更新されていないデータを削除できる仕組みを設ける。

---

## 8. セキュリティ

GitHub Pages上のフロントエンドは信頼できないクライアントとして扱う。

以下を満たすこと。

* Supabase Secret Keyをフロントエンドに含めない
* `service_role` Keyをフロントエンドに含めない
* 他の対戦を任意に更新・削除できないようにする
* 合言葉を平文保存しない
* 対戦参加者以外による操作を可能な範囲で防止する

具体的な実装方式はCodexがSupabaseの推奨方式に基づいて決定する。

---

## 9. 環境変数

フロントエンドからSupabaseへ接続するため、以下の環境変数を使用する。

```env
VITE_SUPABASE_URL=
VITE_SUPABASE_PUBLISHABLE_KEY=
```

ローカル環境では `.env` を使用し、Gitには含めない。

リポジトリには `.env.example` を配置する。

GitHub PagesではGitHub Repository Variablesから同じ環境変数をビルド時に設定する。

開発環境ではローカルSupabaseへの接続情報を設定し、本番環境とは接続先を分離する。

---

## 10. Infrastructure as Code

バックエンド環境は可能な限りコードとして管理する。

### Terraform

Supabase ProjectおよびTerraformで管理可能なSupabaseインフラ設定を管理する。

Terraform関連ファイルは以下に配置する。

```text
infra/terraform/
```

Terraform Stateおよび秘密情報はGitに含めない。

### Supabase Migration

データベース内部の構成はSupabase Migrationで管理する。

対象には以下を含む。

* テーブル
* Index
* Constraint
* Function / RPC
* RLS
* Policy
* Trigger

Migrationは以下で管理する。

```text
supabase/migrations/
```

DB構造をDashboard上の手作業だけで管理せず、Git Cloneした環境でも再現可能にする。

---

## 11. ローカルサーバ

開発用にローカルサーバー環境を構築する。

ローカル環境では、クラウド上の本番Supabaseへ接続せず、ローカルで起動したSupabase環境を使用して開発・動作確認できるようにする。

主に以下をローカルで利用可能にする。

* フロントエンド開発サーバー
* PostgreSQL
* Supabase API
* Supabase Realtime
* その他オンライン対戦に必要なSupabase機能

Supabase CLI等を利用し、リポジトリからローカルバックエンド環境を再現できるようにする。

開発時の構成イメージは以下とする。

```text
Browser
   │
   ▼
Frontend Dev Server
   │
   ▼
Local Supabase
   │
   ├─ Database
   ├─ Realtime
   └─ Backend Functions
```

ローカル環境でも、本番環境と可能な限り同じMigrationおよびバックエンドロジックを使用する。

ローカルCPU対戦の検証では、ブラウザは対戦開始・プレイヤー操作・リタイア要求をEdge Functionへ送信する。Edge Functionは対戦状態を保存し、操作を検証した後にCPU操作を実行して、更新済みの状態とイベントを返す。ブラウザ上でCPU操作や対戦状態の確定を行わない。

開発者がGit Cloneした後、必要なセットアップを行うことでローカルのみでオンライン対戦機能を検証できる状態を目指す。

具体的な起動方法、ポート、Docker構成、スクリプト等はCodexが既存プロジェクト構成を確認して適切に決定する。

## 13. 初期実装範囲

初期実装では以下を実現する。

* Supabase環境構築
* Terraformによるインフラ管理
* MigrationによるDB管理
* 開発用ローカルサーバー環境
* ローカルSupabase環境
* ローカル環境のみでのオンライン対戦動作確認
* ユーザー名入力
* ランダムマッチ
* 合言葉マッチ
* マッチング待機
* 対戦開始
* 対戦相手名表示
* 対戦状態のリアルタイム同期
* 切断・再接続への基本対応
* 対戦終了後のデータ削除
* 放置データの削除

---

## 14. 初期実装対象外

以下は対象外とする。

* アカウント登録
* ログイン
* 永続プロフィール
* カードのバックエンド管理
* デッキのバックエンド管理
* 戦績
* ランキング
* フレンド
* リプレイ
* 観戦
* 対戦履歴
* 永続的なユーザー識別

---

## 15. 実装方針

本仕様書では要件と責務のみを定義する。

以下の詳細は、既存コードおよびSupabaseの推奨方式を確認した上でCodexが適切に設計・実装する。

* テーブル構造
* カラム構成
* RPC / Function構成
* RLS / Policy
* Realtime方式
* 一時プレイヤーIDの管理方法
* 対戦参加者の認証方法
* マッチング時の競合制御
* 切断判定
* データ削除方式
* Terraform Resource構成
* ローカルSupabaseの構成
* ローカルサーバーの起動方法
* 開発用スクリプト
* ローカル環境と本番環境の設定切り替え方法

既存のフロントエンド構造への影響を最小限にし、シンプルで保守しやすい構成を優先する。

また、ローカル開発環境と本番環境で可能な限り同じバックエンド定義を利用し、環境差異による問題を最小限にする。
